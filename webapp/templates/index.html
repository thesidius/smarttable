Camera controls

load status…

auto (meter the dice) searches for the brightest exposure at which the dice faces still stay below saturation, then locks there. It bisects on the live preview inside the tray boundary, so it takes a few seconds and needs the dice to actually be in the tray.

Ordinary auto-exposure meters the whole frame. The tray floor is most of that frame and it is dark, so AE raises brightness until the FLOOR is mid-grey — and the dice, far brighter, blow out. Measured: plain AE clipped 0.233% of pixels, essentially all of them on dice faces; highlight metering chose 117 ms at gain 1.0 and clipped 0.022%. A clipped numeral is unreadable at any resolution.

Exposure time and gain are interchangeable here. Measured on this rig: 47 ms at gain 4.8 and 227 ms at gain 1.0 gave the same floor brightness (131.6 vs 132.1), the same noise (3.26 vs 3.33) and the same clipping (0.23% vs 0.25%). The dice are stationary, so a long exposure costs nothing but preview frame rate. Pick whichever you like and spend the effort on total brightness instead.

Clipping is what to avoid: at gain 1.0, 110 ms clipped no pixels at all, 160 ms clipped 0.06% and 227 ms clipped 0.33%. A clipped numeral is unreadable at any resolution.

Segmentation (SAM2)

Segmentation only — no reading, so this costs a few seconds instead of minutes. When a roll comes back wrong this is the first question to ask, because a mask that merged two dice and a reader that misread a clean crop produce the same symptom. If the dice are each separately tinted below, segmentation was fine and the fault is in the reading.

The old variance/watershed controls are gone. They tuned a method that counted 20 dice for 8 and could not split touching dice at all; SAM2 separated 7/7 of a tight pile. Keeping the sliders would only invite re-tuning something already measured and rejected.

Masks

Each die tinted a different colour is a separate mask. Two dice sharing one tint is a merge; a tinted patch of tray is a false positive.

Isolated crops — exactly what the reader receives

Each die is composited onto neutral grey through its mask, so neighbouring dice are gone rather than merely cropped around. Grey rather than black or white: a hard black border is an artificial edge a reader latches onto, and white blows out against pale dice. These same crops populate the Label tab.

Labelling

Claude Code is slow per die (~10s haiku, ~105s opus) but far more accurate on die TYPE; Ollama answers in ~1s and calls every d12 a d10. For building a labelled set, accuracy matters more than speed.
Suggestions are pre-labels, not ground truth — the model has been verified on two crops only. Every value needs your eyes on it before it becomes training data. Labels append to dataset/labels.jsonl; corrections are just another append.

Read a roll

SAM2 segments each die out of the tray and the reader sees one isolated die at a time -- measured 8/8 dice and 7/7 of a tight pile in ~3s, against a distance-transform count that reported 20 dice for 8. Reads are batched into one call per prompt variant, not one per die. The whole-tray button is the older path, kept for comparison.
Pi captures and counts; {{ vision_model }} reads. Three different prompts are used, not three repeats — at temperature 0 the same prompt returns identical output every time, so repetition proves nothing. Confidence comes from where the prompts disagree and from the camera's independent count, never from the model's own confidence claim, which was measured to say "high" on a die it could not see.

Anthropic API — model

This list is fetched from the Messages API and needs an sk-ant-api key. A Claude Code OAuth token cannot load it - different service. If you are reading via Claude Code, set the model in the card above instead; this one only applies to the Anthropic API provider.

Two credentials, easily confused

sk-ant-oat... is a Claude Code OAuth token and drives claude -p as a subprocess. sk-ant-api... is an API key for the x-api-key header of the Messages API. Both come from Anthropic, both start sk-ant-, and pasting the OAuth token into the API-key field returns 401 invalid x-api-key - which reads like a bad key rather than the right credential at the wrong door. So a credential is filed by what it is, not by which box it was typed into; swap them and it is routed correctly and says so.

Precedence is environment, then the value saved here, then the default. ANTHROPIC_API_KEY in the environment is the kill switch: if a key leaks the fix has to be "set the variable, restart", and that only works if the environment cannot be silently outranked by something this page can write.
